## 面向 Linux 与 Linux + macOS 双平台的隔离方案调研

**读者**：agent 框架 / 平台工程师与架构决策者
**范围**：缺少硬件虚拟化设备节点时，对智能体生成的命令与代码的隔离机制、部署前提与选型
**日期**：2026 年 11 月

---

## 摘要

在缺少 `/dev/kvm` 的机器上为智能体搭建执行环境时，常见的判断跳跃是「跑不了虚拟机，所以做不了沙箱」。本文基于 50 份全文材料（内核与厂商官方文档、独立开源项目说明、学术论文、产品对照，以及一批开箱即用框架的实现者文档）说明：KVM 缺失只关闭了「以 KVM 为后端的轻量虚拟机」这一条路径，并未关闭内核安全模块、系统调用过滤、命名空间、用户态应用内核，也未关闭把执行搬到远端的选项。

真正决定可行性的，是四个必须逐项核对的正交前提：内核版本与内核安全模块配置（Landlock 需 Linux 5.13 及以上且编译/启动期启用）、**带能力的**非特权用户命名空间（bubblewrap 的唯一机制，且「能创建」不等于「带能力」）、是否允许远端执行、以及工具链可裁剪程度。

按平台覆盖分组，结论如下。**仅 Linux** 且零硬件虚拟化，存在五层栈：Landlock、seccomp-bpf 配合 `no_new_privs`、bubblewrap、gVisor 的 systrap 平台、容器与集群原语；每层的一手文档都明确不需要硬件虚拟化，但前提逐级加重，nsjail、Firejail、Sandbox2 与 isolate 只是这套栈的现成封装。**同时支持 Linux 与 macOS** 有三条系统级路径：操作系统原语对配统一调用接口（macOS Seatbelt / Linux bubblewrap+seccomp，Codex 与 sandbox-runtime 均采用）、跨平台虚拟机抽象（libkrun 的 KVM/HVF、Encore crackling 的 Firecracker/VZ）、远端托管沙箱。此外还有一条语言运行时层路径：虚拟 shell 与语言运行时权限模型已有实现者写明的威胁模型，但实现者自述无虚拟机隔离、并要求叠加操作系统或虚拟机边界，因此不是等价的替代方案。开箱即用的 microVM 框架也要单独核对——BoxLite 与 E2B 的自托管形态在 Linux 侧仍要 `/dev/kvm`，ArcBox 在 macOS 侧要求嵌套虚拟化与 M3 或更新芯片；跨平台搬走的是前提，不是消除了它。

网络出口与凭据是与进程隔离并列的第二条边界：出站策略须由执行环境之外的代理或宿主策略强制，DNS 应在域名获批后才解析，凭据宜由策略层注入而非进入客户机；多家产品的公网访问默认开启，配置开关的名字也未必等于它管住的对象。隔离强度取决于完整部署与威胁模型，而非架构标签——「microVM 必然比 gVisor 安全」并不成立。

本文对具体受限宿主的判断均为条件性推论：该环境的实测报告未纳入证据集，框架后端的公开设计记录只说明形态、不能替代宿主探针。第 7 章列出复核后的缺口及补齐后会改变的结论。落地建议的顺序是：先盘点宿主四项前提，再决定是否远端化，随后补出口与凭据边界；跨平台虚拟机抽象的自建成本应放在最后考虑。

**关键词**：智能体沙箱、KVM、Landlock、seccomp-bpf、bubblewrap、gVisor、Seatbelt、libkrun、microVM、运行时层隔离、网络出口隔离、凭据代理

# 第 1 章 没有 `/dev/kvm`，究竟意味着什么

## 常见的判断跳跃

在给智能体（agent）搭建执行环境时，工程师常会先查一次设备节点：

```
ls -l /dev/kvm
```

如果这一行返回「不存在」，很容易顺势得出两个结论：其一是「这台机器跑不了虚拟机」，其二是「所以这里做不了沙箱」。第一个结论通常是正确的，第二个却不是。Firecracker 这类轻量虚拟机监视器确实直接驱动内核的 KVM 接口，因而需要一台具备 `/dev/kvm` 的 Linux 宿主；Mac 从来没有这个设备节点，Firecracker 维护者也明确拒绝了基于苹果虚拟化框架的可行移植，短期内不打算支持 macOS（Encore，2026；Vercel，2026a）。但是，把「KVM-backed microVM」这一条路径关闭，与「无法约束不可信代码」之间，还隔着好几种完全不同的隔离机制。

这种判断跳跃之所以危险，是因为它会把选型引向两个极端：要么彻底放弃隔离，让智能体生成的命令直接在宿主上跑；要么投入大量工程去补硬件虚拟化，而实际上真正卡住部署的可能是另一件事——比如内核版本太旧，或者容器不允许创建带完整能力的用户命名空间。本文要做的，是把「没有 `/dev/kvm`」这个二值判断，还原成一组可以逐项核对的条件。

## 四类方案，两种覆盖范围

结论先摆在前面。在缺少硬件虚拟化的设备上，可用的隔离方案分成两组，划分标准是平台覆盖：

**只在 Linux 上成立、且不依赖硬件虚拟化的一整套分层栈**：从内核的非特权访问控制（Landlock）开始，往上依次是系统调用过滤（seccomp-bpf）、命名空间与文件系统视图（bubblewrap）、用户态应用内核（gVisor 的 systrap 平台），直到无根容器与 Kubernetes 原语。Linux 内核文档、gVisor 官方平台指南、bubblewrap 维护者文档都明确说明，这些机制运行在普通内核能力之上，不需要 `/dev/kvm`（Linux 内核文档，2026；gVisor 项目，2026；containers/bubblewrap，2026）。

**同一方案能同时覆盖 Linux 与 macOS 的系统级路径有三条，另有一条边界更窄的运行时层路径**：第一条是各操作系统原生原语配上一层统一调用接口——macOS 用 Seatbelt，Linux 用 bubblewrap 加系统调用过滤，Windows 用受限令牌，OpenAI 的 Codex 与 Anthropic 的 sandbox-runtime 都采用这个形态（OpenAI，2026a；Anthropic，2026）。第二条是跨平台虚拟机抽象——同一个接口在 Linux 下接 KVM，在 macOS 下接 Hypervisor.framework 或 Virtualization.framework（libkrun，2026；Encore，2026）。第三条是把执行搬到远端，隔离发生在服务端，本地只需网络出口（Vercel，2026b）。第四条是用虚拟 shell 与语言运行时权限模型收窄脚本能力：它已有实现者的一手威胁模型，跨平台且零内核依赖，但实现者明确写着没有虚拟机隔离、建议叠加操作系统或虚拟机边界，所以不是前三条的等价替代（Vercel Labs，2026a，2026b；Deno 项目，2026）。

此外还有一条贯穿所有方案的边界：网络出口与凭据并不由进程隔离自动提供，必须单独设计（OpenAI，2026a；Vercel，2026a，2026b）。

# 第 2 章 判据：四个正交前提，而不是一个开关

## `/dev/kvm` 到底关掉了哪扇门

内核虚拟机（Kernel-based Virtual Machine，KVM）是 Linux 内核里把处理器虚拟化能力暴露给用户态的接口，通常表现为 `/dev/kvm` 设备节点。Firecracker 这类精简设备模型的虚拟机监视器直接调用它来启动一个独立的 Linux 客户内核；gVisor 也有一个可选的 KVM 平台，让它的用户态内核同时充当客户系统与客户机监视器（Vercel，2026a；gVisor 项目，2026）。

关键在于「可选」。gVisor 的平台指南列出三种平台：KVM、systrap 与 ptrace。只有第一种依赖内核 KVM；systrap 依靠 seccomp 的 `SECCOMP_RET_TRAP` 特性把系统调用陷回用户态内核处理，并在 2023 年中取代 ptrace 成为默认平台；ptrace 虽然「即使在不支持嵌套虚拟化的虚拟机里也能工作」，但因上下文切换开销过大已不再受支持（gVisor 项目，2026）。换句话说，同一套应用内核方案，在有无硬件虚拟化的机器上都能跑，只是走不同的平台。

所以 `/dev/kvm` 关闭的只是「以 KVM 为后端的轻量虚拟机」这一扇门。它没有关闭内核安全模块、系统调用过滤、命名空间、用户态内核，也没有关闭「把执行放到另一台机器上」这个选项。

## 四个正交前提

把第 1 章的判断跳跃展开，真正决定某个沙箱能否落地的是下面四个维度。它们彼此独立：一个满足不能推出另一个满足，必须逐项核对。

**一、内核版本与内核安全模块配置。** Landlock 是一个栈式内核安全模块（Linux Security Module，LSM），最早出现在 Linux 5.13，且必须在编译期打开 `CONFIG_SECURITY_LANDLOCK=y`，并在 `CONFIG_LSM` 或启动参数 `lsm=landlock,...` 中启用。它的定位是让「任何进程，包括非特权进程」都能安全地限制自己；规则按文件层级聚合，约束当前线程及其后续子进程，且只能收紧、不能撤销。网络规则是后来逐版本补齐的：TCP 端口规则自 ABI v4 起、UDP 自 v10 起、能力规则自 v12 起（Linux 内核文档，2026）。这意味着「内核是 5.x」不足以判断可用性，还得看 ABI 版本与实际启用的模块。

**二、带能力的非特权用户命名空间（capability-bearing unprivileged user namespace）。** 这是最容易误判的一项。bubblewrap 用它来构造沙箱，让普通用户也能创建隔离环境；历史上它曾支持 setuid 模式以兼容不支持用户命名空间的系统，但该模式已经被移除（containers/bubblewrap，2026）。更微妙的是，某些发行版允许 `unshare(CLONE_NEWUSER)` 成功，却会剥离新命名空间里的能力——Ubuntu 24.04 及以后默认启用的 AppArmor 限制就是这样，而 bubblewrap 与 seccomp 隔离层都需要「带能力的」用户命名空间（Anthropic，2026）。因此「用户命名空间可用」不等于「bubblewrap 可跑」；官方 Codex 文档也说明了缺 `bwrap` 时回退到内置辅助程序，但那个辅助程序同样要求非特权用户命名空间创建能力，Ubuntu 24.04 上还需额外加载 `bwrap-userns-restrict` 配置或调整 sysctl（OpenAI，2026b）。

**三、是否允许把执行搬离本机。** 若允许远端执行，隔离可以完全发生在服务端，本地只需网络出口与凭据；若不允许，就只能在本地内核能力里找方案。这个维度与前两个互不依赖，却常被漏掉，因为它更像架构决策而非技术前提。

**四、工具链可裁剪程度。** 如果智能体的工作负载必须能跑任意原生二进制、包安装、git 与容器构建，那么虚拟 shell 与语言运行时层的方案基本不适用；如果可以限定工具链，这一层能提供跨平台且零内核依赖的约束。实现者自己的威胁模型把「没有虚拟机隔离」「可选解释器默认关闭」「宿主提供的钩子属于受信面」写成前提（Vercel Labs，2026a，2026b；Deno 项目，2026），因此这一项决定的是能省掉多少工具链，而不是能省掉多少外层边界。

## 几个必须先分清的词

**沙箱**在本文里始终指对智能体生成的命令或代码的强制约束，包括文件系统可见性、网络出口、进程关系与系统调用面。它不包含应用自身的工具权限系统（例如「允许读哪些文件」的应用层配置）——两者是独立的边界，不能互相替代。

**隔离边界**指约束由哪一层强制：内核安全模块、操作系统进程原语、用户态应用内核、硬件虚拟化、语言运行时，或远端服务。这六层不是强弱排序，而是不同的信任模型；第 6 章会说明为什么不能按架构标签给强度排名。

**平台支持**指同一方案（或同一套调用接口）能否在 Linux 与 macOS 上都成立。「Linux 上有一层、macOS 上有另一层，由一个统一接口包装」算双平台方案；「两台机器各装一套完全不同的东西」不算。

## 判据怎么用

后三章按这个判据组织：第 3 章的每一层都会标明它要求上面哪些前提；第 4 章的四条双平台路径按「是否另需本地硬件虚拟化」区分；第 5 章处理与进程隔离并列的第二条边界。读者若已有一台具体机器，建议先按这四项逐条核对，再进入选型——否则容易在前提未知的情况下比较方案的强弱。

# 第 3 章 仅 Linux：零硬件虚拟化的分层栈

第 2 章给出的判据里，前两项都是 Linux 内核能力。把这两项打开，就得到一整套不需要 `/dev/kvm` 的分层栈。下面按前提由轻到重排列；排序表达的是「部署所需条件递增」，不是隔离强度递增。

## 第一层：Landlock，非特权进程自我约束

Landlock 的定位与其他机制都不同：它不创建环境，而是让进程主动交出自己本来拥有的全局权限。规则集一旦施加，就约束当前线程及其所有后代，且不可撤销；规则覆盖文件层级，较新的 ABI 还覆盖 TCP/UDP 端口与 Linux 能力（Linux 内核文档，2026）。

它对宿主的要求最低：不需要 root，不需要用户命名空间，不需要 `CAP_SYS_ADMIN`。代价是「最低」不等于「没有」——内核必须 ≥5.13、编译期启用该模块、启动参数里包含 `landlock`，且想用网络规则还得查 ABI 版本。对内核版本较旧的宿主，这一层直接不可用。另一个限制是能力形状：Landlock 表达的是「允许访问哪些资源」，无法凭空构造一份与宿主不同的文件系统视图，也没有进程间隔离。

## 第二层：seccomp-bpf 与 `no_new_privs`

系统调用过滤（secure computing with Berkeley Packet Filter，seccomp-bpf）用一个动态编译的 BPF 程序限制进程可发起的系统调用。要在没有特权的前提下施加过滤器，启动器会设置 `no_new_privs` 标志；该标志由子进程继承，防止通过执行 setuid 程序获得额外权限（OpenAI，2026a）。

Codex 的 Linux 实现给了这一层很具体的用法：网络禁用时拦截 `connect(2)`、`bind(2)` 等调用；启用代理时允许 IP 套接字，但默认阻止创建独立的 Unix 域套接字，以免误触宿主资源（OpenAI，2026a）。这说明 seccomp 擅长的是「收窄能力面」，而不是「提供文件系统隔离」——后者需要下一层。

## 第三层：bubblewrap，构造文件系统视图与命名空间

bubblewrap 用非特权用户命名空间搭建环境，让普通用户也能创建隔离的挂载视图。Codex 用它按权限档案拼出一份文件系统：`--bind` 给可写路径、`--ro-bind` 给只读路径、用指向 `/dev/null` 的 `--ro-bind-data` 或权限为零的 tmpfs 表达拒绝；再配合 `--unshare-ipc`、`--unshare-pid`，以及在需要禁网或走代理时的 `--unshare-net`（OpenAI，2026a）。Anthropic 的 sandbox-runtime 在 Linux 侧也是 bubblewrap，加上 `socat` 做代理桥接、`ripgrep` 做拒绝路径扫描，支持版本要求 0.4.0 以上（Anthropic，2026）。

这一层的两个限制必须记住。其一，维护者自己写明「bubblewrap 不是一个带既定安全策略的完整现成沙箱」，保护程度完全取决于传给它的参数（containers/bubblewrap，2026）。其二，前提正是第 2 章那项容易误判的条件：用户命名空间得带能力。sandbox-runtime 的文档进一步说明，它会用 seccomp 拒绝沙箱内进程再创建用户或挂载命名空间——否则只读绑定挂载可以被从新的挂载命名空间里拆掉；代价是 Chromium/Electron 自带的命名空间沙箱、无根 podman、嵌套 bubblewrap 全部失效（Anthropic，2026）。这是一个真实的功能取舍，不是可以顺手关掉的告警。

## 第四层：gVisor 的 systrap 平台，用户态应用内核

gVisor 在沙箱代码与宿主内核之间插入一个应用内核（Sentry）。Sentry 自己实现了一部分 Linux 系统调用接口并维护沙箱的进程状态，例如可以由自己的状态回答「进程号是多少」，只在必要时使用受限的宿主调用，而不是把应用的调用直接转发给宿主内核（Vercel，2026a）。

第 2 章已经说明 systrap 不依赖硬件虚拟化，且是 2023 年以来的默认平台。它的适用边界也清楚：Sentry 实现的是系统调用接口的**子集**，不支持某个调用不必然导致运行时失败，因为库可能检测到并改用替代路径，所以需要针对真实工作负载测试，而不是只看解释器能否启动（Vercel，2026a）。资源限制依赖宿主 cgroups，网络策略也要在沙箱之外落实（Vercel，2026a）。若已经运行容器，gVisor 的 `runsc` 接入可以保留既有工具链。

## 第五层：容器与集群原语

再往上需要容器守护进程或 Kubernetes。Kubernetes 的 Agent Sandbox 把智能体放进以 gVisor 用户态内核为底、可选 Kata Containers 的轻量虚拟机里，用 `Sandbox` 自定义资源表示一个有状态、长生命周期、身份稳定的单实例（Eunomia，2026；Kubernetes SIG Apps，2026）。自托管的 OpenSandbox 提供统一的生命周期接口，本地运行要求 Docker，Kubernetes 上的 Firecracker 档位能做到 64 毫秒的创建中位时延，但那一档仍要 KVM（OpenSandbox，2026）。

这一层的前提最重：需要守护进程、容器运行时，乃至集群。它适合已有这些基础设施的团队，不适合一台权限受限的单机。

## 现成的进程沙箱封装

上面五层说的是机制，工程上不必从零拼装。Google 的 nsjail 把 UTS / MOUNT / PID / IPC / NET / USER / CGROUPS / TIME 命名空间、`chroot()` 与 `pivot_root()`、Kafel 写的 seccomp-bpf 策略、cgroup v1/v2 资源限制打包成四种执行模式（Google/nsjail，2026）。Firejail 是 SUID 程序，用命名空间、seccomp-bpf 与 capabilities 给进程及其后代一份私有的内核资源视图，并声明内核 3.x 以上即可运行（Firejail，2026）。Google 的 Sandboxed API / Sandbox2 走的是库级隔离：把单个 C/C++ 库放进独立进程，用紧定义的策略代替覆盖整个程序的系统调用面（Google/Sandbox2，2026）。ioi/isolate 面向竞赛判题，明确依赖 Linux 命名空间与控制组（ioi/isolate，2026）。

这些项目降低的是接入成本，不是前提要求。它们仍落在第二、三层：命名空间、能力集与系统调用过滤是否被宿主允许，决定它们能否启动。Kubernetes 的 Agent Sandbox 也属同一类封装——它自述只是编排层，底层隔离委托给 gVisor 或 Kata 的运行时类（Kubernetes SIG Apps，2026）。换句话说，看到「现成沙箱」四个字，仍然要回到第 2 章那四项前提逐项核对。

## 这一章能回答什么

如果宿主是 Linux、内核 ≥5.13 且 Landlock 已启用，即使完全没有用户命名空间，也仍有第一层可用；如果还具备带能力的非特权用户命名空间，第二、三层可用；如果允许运行 `runsc`，第四层可用，且不需要硬件虚拟化；如果已有容器平台，第五层可用。反过来，若内核版本低于 5.13、Landlock 未启用、用户命名空间被剥离能力，那么这五层连同它们的现成封装都在前提出局——此时问题不在「哪个更强」，而在「本地是否还有任何内核边界可用」。第 4 章的路径三正是为这种情形准备的。

# 第 4 章 Linux 与 macOS 双平台：三条系统级路径与一条运行时层路径

第 3 章的分层栈几乎全部建立在 Linux 内核能力上。若要同一套方案同时覆盖 Linux 与 macOS，思路必须换掉：要么在两端各用原生原语、由统一接口抹平差异，要么把虚拟化能力抽象成跨平台接口，要么干脆让隔离发生在别处。下面三条系统级路径都有一手实现文档支撑；第四条是语言运行时层，同样已有实现者的说明，但边界明显更窄，不能与前三条画等号。

## 路径一：操作系统原语对 + 统一调用接口

这是目前部署最广、文档最完整的一条。核心形态是：调用方只面对一个接口，接口按操作系统选择不同的原生机制。

OpenAI 把 Codex 的命令执行从 `subprocess.Popen()` 换成 `spawn_command_under_sandbox()`，传入权限档案与（需要时）网络代理，返回子进程句柄。macOS 侧走 Seatbelt，通过 `/usr/bin/sandbox-exec -p <profile> -- <program>` 施加 SBPL 编写的策略；Linux 侧由 `codex-linux-sandbox` 协调 bubblewrap 与 seccomp-bpf；Windows 侧用原生沙箱，WSL2 里复用 Linux 实现（OpenAI，2026a，2026b）。子进程继承这些限制，因此智能体派生出的整棵进程树都在边界内。

Anthropic 的 sandbox-runtime 是同一形态的另一个独立实现：macOS 用 `sandbox-exec` 动态生成 Seatbelt 策略，Linux 用 bubblewrap 做文件系统与网络命名空间隔离，Windows 侧（alpha）用受限令牌、WFP 出站过滤与显式访问控制项。它自我定位为「无需容器」的操作系统级约束工具（Anthropic，2026）。

这条路径的优点是不需要 `/dev/kvm`、不需要容器、不需要特权安装，且两端都有真实产品在跑。限制也很具体：

- macOS 的 `sandbox-exec` 已被苹果标记为 deprecated，SBPL 也没有面向第三方的官方文档；但 macOS 仍自带 `/usr/share/sandbox` 策略，Chrome/Chromium 继续使用 Seatbelt，因此 Codex 明确表示会在可预见的将来继续用它（OpenAI，2026a）。这是「当前可用但未获长期承诺」的状态，不是稳定 API。
- 机制只包裹命令执行。Codex 文档提醒，MCP server 之类的常驻进程需要调用方手动包裹，不会自动进入沙箱（OpenAI，2026a）。
- 两端能力并不对称。例如拒绝路径的通配符在 bubblewrap 上需要展开成具体路径，且命令启动后新出现的匹配路径不会自动加入该次限制（OpenAI，2026a）。

## 路径二：跨平台虚拟机抽象，本地仍可无 KVM

如果目标是硬件级边界，又必须在 macOS 上本地跑，可以把「启动一个轻量 Linux 虚拟机」这件事抽象成统一接口，让不同平台各自接自己的虚拟化框架。这里的「本地仍可无 KVM」指的是 macOS 侧改由苹果框架提供虚拟机边界；Linux 侧若要用同一套 KVM 后端，仍然需要 `/dev/kvm`。

libkrun 是一个可嵌入的动态库，官方说明它「在 Linux 上使用 KVM、在 macOS/ARM64 上使用 HVF、在 Windows 上（规划中）使用 WHP」来运行部分隔离的进程；设备集压到 virtio-net、virtio-vsock、virtio-balloon 等最小组合，并提供透明套接字伪装与 virtiofs 目录共享。它被 crun（Podman 的 `--runtime=krun`）、krunkit、muvm 等项目使用（libkrun，2026）。库文档同时给出一条重要安全提醒：虚拟机边界**不限制通过设备暴露给客户机的宿主资源**，因此必须另外收紧 VMM 自身的宿主权限与暴露路径；透明套接字伪装使用的是 VMM 的宿主网络权限（libkrun，2026）。

Encore 的 crackling 是另一条独立实现：一个 microVM API，Linux 后端是 Firecracker，macOS 后端是苹果 Virtualization.framework（VZ）。两端实现同一个 `MachineBackend` 契约（`start`/`shutdown`/`pause`/`resume`/`snapshot`/`wait`/`dispose`/`connect_vsock`），客户机里跑同一个 agent，通过 `AF_VSOCK` 通信，支持命令执行、交互式 shell、双向文件拷贝与端口转发（Encore，2026）。

这条路径的价值是「同一 API、两端硬件边界」，代价却常被低估：

- 能力不对等，且必须在启动前显式协商。crackling 的每个后端会在创建任何机器之前报告当前宿主支持哪些特性；VZ 不支持进程脱离后重新接管（adoption）、不支持快照恢复、没有 MMDS 与宿主 tap 设备，VZ 侧快照还受权限授权限制，而 VZ 自带 NAT、virtiofs 与 Rosetta（Encore，2026）。
- 工程量大。Encore 记录了重建 Linux 镜像工具链、VZ 对象不可跨线程（`!Send + !Sync`）因而必须全局串行队列、客户机内核模块 vermagic 必须严格匹配、`AF_VSOCK` 模块需在 `/init` 里先行加载等一长串问题（Encore，2026）。
- 平台版本要求具体。苹果的 `container` 要求 Apple silicon 且 macOS 26 以上，用轻量虚拟机逐个运行 Linux 容器（Apple，2026）。在 M3 或更新的芯片、macOS 15 上，还可以在 Linux 虚拟机内部获得 `/dev/kvm`，从而原样运行 Firecracker（Encore，2026）。

需要点明一个易混淆处：libkrun 走的是 HVF（Hypervisor.framework），crackling 走的是 VZ（Virtualization.framework）。两者都在 macOS 上提供虚拟机边界，但框架、授权要求与能力集不同，不能合并成「苹果虚拟化」一个方案。

### 开箱即用框架的前提矩阵

近两年出现的一批开源项目把 microVM 包装成可直接嵌入的库、命令行工具或 Kubernetes 资源。它们降低了接入成本，却没有把虚拟化前提变没。下表按实现者自己的说明逐项列出：

| 项目 | 隔离形态 | Linux 侧前提 | macOS 侧前提 | 对无 KVM 设备的含义 |
|---|---|---|---|---|
| BoxLite（2026） | 每个 Box 一个自带内核的 microVM，可当库嵌入、无守护进程 | KVM 可用（`/dev/kvm` 可访问） | Apple Silicon + Hypervisor.framework | 跨平台不等于无 KVM；Linux 侧前提原样存在 |
| ArcBox（2026a，2026b；arcbox-hypervisor，2026） | Firecracker microVM，每个沙箱有独立内核；hypervisor 抽象层 Linux 走 KVM、macOS 走 VZ | KVM（`/dev/kvm`） | 嵌套虚拟化 + Virtualization.framework 后端 + M3 或更新芯片 + macOS 15+；其他硬件或 HVF 后端，沙箱操作一律 `FAILED_PRECONDITION` | 把硬件要求移到特定 Mac，且叠加了嵌套虚拟化条件 |
| E2B（2026） | 每沙箱一个 Firecracker microVM，支持快照恢复、暂停与分叉 | 自托管 Embed 形态是「单台带 KVM 的 Linux 宿主」 | 不适用（服务端形态） | 自托管仍需 KVM；托管形态则是把隔离搬到服务端 |
| microsandbox（2026） | 本地 microVM，宣称覆盖 Linux / macOS / Windows | 硬件隔离档需本机虚拟化能力 | 硬件隔离档需本机虚拟化能力 | 「跨平台」指安装面，不表示前提被消除 |
| Kubernetes SIG Apps（2026） | `Sandbox` 自定义资源与控制器，管理有状态单实例 | 只做编排，明确把底层隔离委托给 gVisor / Kata 等运行时类（RuntimeClass） | 同左 | 编排层本身不提供边界，必须另选运行时类 |

ArcBox 的文档还给出可直接核对的生命周期事实：`/workspace` 初始为空、不挂载宿主目录、停止或删除即销毁全部内容，单文件传输上限 256 MiB；在 M5 Max、macOS 26、1 vCPU / 512 MiB 的配置下，预热创建约 50 ms、冷启动约 640 ms（ArcBox，2026b）。E2B 的开源运行时则说明每个沙箱带独立 cgroup、网络命名空间、nftables 出口防火墙与域名名单（E2B，2026）。这类数据让「开箱即用」可以被验证，而不只是宣传语。

由此得到一条实用判据：看到「支持 Linux + macOS」时，先问虚拟化能力落在哪一侧、那一侧的硬件与系统版本是否满足，再问它是否只是把执行搬到了服务端。Daytona 仓库已经归档、最终开源版本停在 v0.190.0（Daytona，2026），也提醒我们生态清单里的「活跃项目」需要按仓库状态复核，而不能只看功能描述。

## 路径三：远端执行，本地零虚拟化要求

第三条系统级路径干脆不在本机做硬件隔离：创建环境、写文件、执行命令、取回输出都通过 SDK，隔离发生在服务端。Vercel 的横向对照列出的七家里，Vercel Sandbox 与 E2B 用 Firecracker microVM，Daytona 用容器或虚拟机档位，Modal 用虚拟机或 gVisor（GPU 场景需 gVisor），Cloudflare Sandboxes 用 microVM 内的 Linux 容器或 Dynamic Worker，Blaxel 用虚拟机，Fly.io Sprites 用硬件隔离的 Linux 虚拟机（Vercel，2026b）。OpenSandbox 给出自托管版本：统一接口从本地 Docker 平滑移到 Kubernetes，配多语言 SDK、命令行工具与 MCP 接入（OpenSandbox，2026）；E2B 则把云端那套 Firecracker 运行时完整开源，既可在自己的带 KVM 机器上跑，也可直接用托管服务（E2B，2026）。

对本地设备来说，这条路径的前提只有网络出口与凭据，不需要 `/dev/kvm`，也不需要任何内核能力。它还有两种接线方式：可以把整个智能体放进沙箱，也可以把智能体留在应用里、只把生成的代码送过去执行（Vercel，2026a）。后者对「宿主保留模型凭据、客户机只提供 shell 与文件系统」的框架形态尤其贴合。

代价是把信任边界移到了供应商与网络策略上，而且默认行为往往不安全——第 5 章专门展开这一点。

## 路径四：语言运行时层，有实现但不是操作系统边界

第四条路径与前三条不在同一层：它不改变进程对宿主的权限，而是把「能执行什么」限制在一个解释器里。

Vercel Labs 的 just-bash 用 TypeScript 实现 bash 解释器与内存文件系统，供智能体调用。包 README 的安全模型直接写明「所有执行都在没有虚拟机隔离的情况下发生」，默认关闭网络，启用时按 URL 前缀与 HTTP 方法白名单校验，Python 与 JavaScript 执行也默认关闭（Vercel Labs，2026b）。配套的威胁模型把脚本作者、外部数据与依赖供应链列为对手，逐项给出信任边界、可能被利用的途径与执行限额（输入大小、循环次数、命令数、字符串长度、线性时间正则）；同一份文档也把宿主提供的文件系统钩子、Node.js 运行时与操作系统内核列为「受信、不在运行时防护范围内」，并注明可选的 CPython WASM 内存不受 Node worker 资源限制可靠约束，需要进程或容器隔离（Vercel Labs，2026a）。

Deno 是同一层的另一份独立一手实现：默认沙箱，权限用 `--allow-*` / `--deny-*` 按资源细分；官方文档同时点明 `--allow-run` 与 `--allow-ffi` 会绕过沙箱，并建议执行完全不可信的代码时叠加降权 Web Worker、操作系统原语（chroot、cgroups、seccomp）与虚拟机或轻量虚拟机（gVisor、Firecracker）（Deno 项目，2026）。

所以这一层不宜再写成「零一手证据的候选方向」，但也不能与前三条并列为等价方案。它约束的是脚本能调用哪些解释器内能力，不是进程能碰宿主哪些资源；任意原生二进制、包安装、git 与容器构建通常不在能力范围内。两份实现者文档都把外层操作系统或虚拟机边界列为前提，恰好印证第 5 章的判断：运行时层更适合做收窄工具链的附加约束，而不是隔离边界的替代品。

## 四条路径如何取舍

先看是否允许远端执行：允许则路径三最省宿主改造，且是本地零 KVM 时唯一能达到硬件级边界的方式。不允许、且只需要包裹命令执行，则路径一最轻，代价是接受 macOS 侧的 deprecated 状态与两端能力差异。需要独立客户内核、又必须在 macOS 本地跑，则选路径二，但要预算自建镜像工具链、能力协商与硬件代际要求。若工作负载可以限定为脚本与数据处理、且已另有外层隔离，路径四能显著降低工具链成本，但不能充当那层隔离本身。第 5 章会补上四条路径共有的第二条边界。

# 第 5 章 另一半边界：网络出口与凭据

前两章讨论的都是「进程能碰什么」。但智能体造成的数据外泄，很多时候不是通过读写文件，而是通过一次对外请求。把网络当成进程沙箱的附属配置，是这类系统里最常见也最昂贵的设计疏漏。这一章单独处理它，因为进程隔离与出口控制是两条独立的边界：Vercel 明确写过，无论 gVisor 还是 microVM，都**不会自动拒绝出站网络访问**，也不会替业务系统执行权限判断（Vercel，2026a）。

## 代理式出口过滤怎么工作

Codex 的做法是一个可复用的参照。启用网络限制时，harness 启动一个网络代理，并把沙箱配置成「只允许连到这个代理、禁止直连外部主机」。代理同时起 HTTP 与 SOCKS5 两种监听，把地址通过 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 以及若干应用专用变量注入被启动的进程；代理按权限档案里的域名规则决定是转发、拒绝，还是挂起请求交给调用方审批（OpenAI，2026a）。

两个细节值得注意。第一，**域名规则优先于 DNS 解析**：代理只在判定该主机名被允许或已获批准后，才去解析它。理由是「连 DNS 查询本身都可能泄露编码在主机名里的信息」（OpenAI，2026a）。第二，即使这样也不彻底——过宽的 wildcard 规则或允许访问 DNS 服务，仍可能留下基于 DNS 的隐蔽外泄通道（OpenAI，2026a）。Linux 侧还要配合 `--unshare-net` 与 seccomp 过滤，让代理成为唯一可达的出口（OpenAI，2026a）。

Anthropic 的 sandbox-runtime 采用同样的代理式网络过滤，Linux 侧靠 `socat` 把代理桥接进网络命名空间，Windows 侧用机器级 WFP 出站过滤配合受控的回环端口范围（Anthropic，2026）。

## 默认配置往往是「允许」

这是最需要写进部署清单的一条。Vercel 的七家对照里，Vercel Sandbox 的文档明确写着公网访问**默认允许**，需要按任务显式配置 deny-all 或目标策略；E2B 的联网控制同理，互联网访问**默认开启**，要主动关闭或设置允许/拒绝名单（Vercel，2026b）。也就是说，选了一家 microVM 产品，并不等于拿到了 deny-by-default 的出口策略。

自托管 Firecracker 也一样：它不过滤网络流量，网络策略要由宿主落实；生产部署还应使用 jailer 或同等强度的约束来限制 Firecracker 进程本身（Vercel，2026a）。libkrun 的透明套接字伪装同理，用的是 VMM 的宿主网络权限，文档直接要求收紧 VMM 的网络权限（libkrun，2026）。

还有一种更隐蔽的坑：**配置开关的名字不等于它管住的对象**。BoxLite 的集成指南写明，`SecurityOptions.network_enabled` 只撤销宿主侧沙箱自身的网络授权（macOS 用 Seatbelt、Linux 用 Landlock），「并不会让客户机断网」；要让客户机离线，必须把出站网络模式设为 disabled，而且 `network_enabled=False` 与客户机网络开启同时出现会被直接拒绝（BoxLite，2026）。同一份指南还给出 `jailer_enabled`、seccomp、文件描述符/进程/内存/CPU 上限与 `SecurityOptions.maximum()` 预设，并提醒超时后必须显式终止执行，否则客户机里的进程会继续跑（BoxLite，2026）。若只看一个布尔开关就宣布「已断网」，出口边界其实从未建立。

正向的例子也存在。E2B 的开源运行时给每个沙箱配独立 cgroup、网络命名空间、nftables 出口防火墙与 SNI/Host 域名允许/拒绝名单，把出口策略做成运行时的一部分，而不是留给调用方事后补（E2B，2026）。这说明默认拒绝并非做不到，只是需要显式设计与核对。

## 凭据不要进客户机

第三条边界是凭据。Vercel Sandbox 的防火墙在网络策略之外还提供 credential brokering：外部请求由策略层注入凭据，使代码能调用一个需要认证的 API，却拿不到原始密钥（Vercel，2026b）。Vercel 的另一篇文档把这个模式描述得更完整：把外部动作的授权留在应用与授予该动作的服务里，而不是放进执行环境（Vercel，2026a）。E2B 的运行时把这条原则写进数据结构：密钥只作为控制面元数据存在，值不经过 API、日志或链路追踪，工作负载用短期令牌换取权限（E2B，2026）。

这与「客户机只提供 shell 与文件系统、宿主保留模型凭据」的框架形态是同一个思路。把密钥放进沙箱环境变量，等于把最需要保护的东西交给了最不可信的代码；即便进程沙箱没有逃逸，一次被允许的出站请求就足以把它送出去。

## 可复用的检查清单

综合上述材料，无论选第 3 章的哪一层还是第 4 章的哪条路径，都建议逐项确认：

1. **默认出口是什么**。若是「允许」，改成默认拒绝，再按需开白名单；同时核对所用开关到底约束宿主沙箱还是客户机本身。
2. **域名规则在哪里执行**。应在进程之外、由代理或宿主策略执行，而不是靠智能体自觉遵守。
3. **DNS 何时解析**。应在域名获批之后；同时检查是否留了可访问 DNS 服务的口子。
4. **凭据是否进入了执行环境**。优先用策略层注入，避免把长期密钥放进环境变量或客户机文件系统。
5. **子进程与常驻进程是否都受控**。代理地址靠环境变量继承，绕过代理的直连要靠 seccomp / 网络命名空间 / WFP 一起封住；MCP server 之类常驻进程要显式包裹（OpenAI，2026a）。
6. **资源限制是否由宿主落实**。gVisor 的资源限制依赖宿主 cgroups（Vercel，2026a）；虚拟机方案要收紧 VMM 自身的权限，并确认超时能真正终止客户机里的进程。

## 为什么单列一章

在本次证据集里，网络与凭据是独立来源数量最多、可交叉核对程度最高的一部分：既有实现细节（OpenAI，2026a）、可核查的产品默认配置（Vercel，2026b）、厂商对架构界限的立场（Vercel，2026a），也有第二家独立实现（Anthropic，2026）；补充材料又带来实现级的开关语义反例（BoxLite，2026）与默认细粒度出口策略的正向实现（E2B，2026）。相比之下，某些「哪种架构更安全」的说法只有单一厂商立场。因此把它与进程隔离并列，而不作为附注——这也直接影响第 6 章的决策树：一个进程边界很强的方案，若出口默认全开且把密钥放进环境变量，整体安全性可能低于一个边界较弱但默认拒绝出口的方案。

# 第 6 章 对照、决策树与常见误判

## 定性对照矩阵

下表按第 2 章的规范维度汇总。它给的是「边界类型 / 前提 / 平台」，不是强度排名；理由见下一节。

| 方案 | 隔离边界 | 平台 | 本地需硬件虚拟化 | 关键前提 | 主要局限 |
|---|---|---|---|---|---|
| Landlock | 内核安全模块 | Linux | 否 | 内核 ≥5.13、`CONFIG_SECURITY_LANDLOCK=y`、启动参数含 `landlock` | 规则只收紧不可撤销；网络能力看 ABI 版本；不构造文件系统视图 |
| seccomp-bpf + `no_new_privs` | 系统调用过滤 | Linux | 否 | 可设置 `no_new_privs`；过滤器由启动器施加 | 只收窄调用面，不提供文件隔离 |
| bubblewrap | 命名空间 + 挂载视图 | Linux | 否 | **带能力的**非特权用户命名空间 | 安全程度完全取决于参数；嵌套命名空间沙箱会失效 |
| gVisor `systrap` | 用户态应用内核 | Linux | 否 | seccomp 的 `SECCOMP_RET_TRAP`；宿主 cgroups | 只实现系统调用子集；网络策略须在沙箱外落实 |
| 容器 / Kata / Agent Sandbox | 容器运行时或集群原语 | Linux | 否（Kata 档需 KVM） | 容器守护进程或 Kubernetes | 前提最重，不适合权限受限单机 |
| OS 原语对 + 统一接口 | 各 OS 原生原语 | Linux + macOS（+ Windows） | 否 | macOS Seatbelt；Linux bwrap/seccomp；Windows 受限令牌 | `sandbox-exec` 已 deprecated；只包裹命令执行；两端能力不对称 |
| 跨平台虚拟机抽象 | 硬件虚拟化 | Linux + macOS（+ Windows 规划） | macOS 侧否（HVF/VZ） | Apple silicon、较新 macOS 或 Linux KVM | 需自建镜像工具链；VZ 与 Firecracker 能力不对等 |
| 远端 / 托管沙箱 | 服务端隔离 | 任意（本地无要求） | 否 | 网络出口与凭据 | 信任边界移到供应商；默认公网常为 allow |
| 语言运行时层（受限路径） | 解释器内的能力模型 | 跨平台 | 否 | 虚拟 shell / 权限开关、默认关网、可裁剪工具链 | 实现者自述无虚拟机隔离；任意原生二进制/包安装/git 通常不可用；需另有外层边界 |
| 开箱即用 microVM 框架 | 硬件虚拟化的框架封装 | Linux + macOS | Linux 侧仍需 `/dev/kvm`；macOS 侧需 Apple 芯片与新系统 | 框架自身的运行时与虚拟化后端 | 跨平台搬走的是前提而非消除；编排层本身不提供边界 |

新增两行说明同一件事：「开箱即用」降低接入成本，「跨平台」改变前提所在的位置，两者都不改变第 2 章的四项判据。运行时层之所以单列，是因为它与操作系统进程沙箱不在同一层，不能按同一列去比强弱。

## 决策树：先问三个问题

**第一问：允许把执行搬离本机吗？** 若允许，第 4 章路径三是本地零 KVM 前提下唯一能达到硬件级隔离的方式，且宿主改造最小。此时要把精力放在第 5 章的六项出口检查上，而不是继续寻找本地内核能力。若不允许，进入第二问。

**第二问：宿主的四个前提分别是什么状态？** 按第 2 章逐项核对：内核版本与 Landlock 是否启用、带能力的非特权用户命名空间是否可用、是否有 `CAP_SYS_ADMIN`、工具链是否可裁剪。只要内核 ≥5.13 且 Landlock 已启用，就有第一层；若还具备带能力的用户命名空间，第 3 章的第二至四层依次可选。若四项全部不满足，本地内核方案在第 3 章的框架里都出局，只能退到应用层策略并明确标注「无隔离」，或者重新评估第一问。

**第三问：需要的是「包裹命令」还是「独立客户内核」？** 若只是让智能体的 shell 命令受限，第 4 章路径一最轻；若工作负载需要独立的 Linux 客户内核、会变动的工具链或 GPU，才考虑路径二或托管 microVM；若工作负载能限定为脚本与数据处理，可把运行时层作为附加约束，但仍要确认外层边界确实存在。选定框架后还要回查一次第 4 章的前提矩阵：它在目标平台上究竟要 `/dev/kvm`、Apple 芯片与新系统，还是编排层另配的运行时类。Vercel 给出的判据是工作负载相关而非架构标签相关：固定工具链可先在 gVisor 下测完整环境，需要独立客户内核时才倾向 microVM（Vercel，2026a）。

## 常见误判之一：架构标签等于隔离强度

「microVM 一定比 gVisor 安全」是个流传很广的判断，但 Vercel 的对照文章直接给出否定回答：安全性取决于完整部署，包括实现、宿主配置以及授予工作负载的访问权限（Vercel，2026a）。两种边界面对的威胁不同——用户态内核把应用与宿主系统调用面隔开，虚拟机则要求攻击者先突破客户内核再跨越虚拟化边界；哪一方更弱，取决于各自的宿主配置与暴露接口。

需要说清证据强度：这个否定判断主要来自一家厂商的分析。学术界有可用于检验沙箱有效性的工具——SandboxEval 提供了 51 个手工构造的用例，覆盖敏感信息泄露、文件系统操纵与外部通信，用来判断某套评估基础设施是否适合执行不可信代码（SandboxEval 作者，2025）——但它并没有比较 microVM 与 gVisor。因此本文保留「应按威胁模型与部署配置评估」这一主张，不宣称已有独立基准证明了孰优孰劣。

## 常见误判之二：把两份同源文档当成两个独立来源

裁定 Codex 的 Linux 后端时，一份 2026 年 5 月的社区清单把它写成「Landlock + seccomp」，而 OpenAI 自己的工程文章与 CLI 文档都写明是 bubblewrap + seccomp-bpf，并给出了完整的命令行链与 `--unshare-*` 参数（OpenAI，2026a，2026b）。结论应以一手文档为准。

但这里有个容易犯的推理错误：不能说「因为 OpenAI 有两份文档，所以是两份独立证据」。它们同属一个机构、描述同一个实现，属于同一来源。真正的独立依据是三个不同组织的实现一致指向 bubblewrap：bubblewrap 维护者文档定义机制，Anthropic 的 sandbox-runtime 与 OpenAI 的 Codex 各自独立采用了它（containers/bubblewrap，2026；Anthropic，2026；OpenAI，2026a）。这份社区清单作为孤例二手描述保留，不并入结论。至于「早期版本是否曾用过 Landlock」，目前没有一手证据，不能写成事实。

## 常见误判之三：用户命名空间可用就够了

第 2 章已说明 Ubuntu 24.04 及以后允许创建用户命名空间却剥离其能力，而 bubblewrap 与 seccomp 隔离层需要带能力的命名空间（Anthropic，2026）。此外 OpenBSD 风格的容器环境里，`CLONE_NEWUSER` 成功但 `CLONE_NEWNS`/`CLONE_NEWPID`/`CLONE_NEWNET` 全被拒绝的情形也完全可能存在——「一项探针通过」不足以推出「bubblewrap 可跑」。判据应写成四项前提的组合，而不是一次 `unshare` 的退出码。

## 常见误判之四：应用级隔离架构等价于操作系统沙箱

IsolateGPT 提出 hub-and-spoke 执行隔离架构，把第三方应用放进隔离环境、由可信中枢路由请求，并报告「四分之三的测试查询开销低于 30%」且功能无损（Wu 等，2025）。这类工作的价值在于证明执行隔离在智能体系统里可行且有架构蓝图；但它用的是进程级隔离，研究的是应用间的数据与能力边界，不能拿来论证内核沙箱的边界强度。把两类「隔离」混为一谈，会导致用错威胁模型。

## 小结

决策顺序是「是否允许远端 → 宿主四项前提 → 需要命令包裹还是独立客户内核」，再用工具链可裁剪程度决定是否叠加运行时层，最后把第 5 章的出口与凭据检查作为所有分支的共同必选项。这个顺序里没有任何一步需要按架构标签给强度排名；需要比较的是前提、能力与代价。第 7 章转而说明，本次证据集在哪些地方还撑不起更确定的说法。

# 第 7 章 证据边界与尚未解决的问题

前六章给的是方案族与判据。这一章要说清哪些结论有扎实支撑、哪些只是条件性推论，以及还有哪些材料一旦补齐就会改变结论。把边界写明白，比多列几个方案更有用。

## 结论的强度分层

**有官方规范与多个独立实现共同支撑的**：第 2 章的四项前提、第 3 章的五层栈及其硬前提、第 4 章路径一与路径二的机制细节、第 4 章开箱即用框架的硬件前提、第 5 章的代理式出口与默认公网行为。这些陈述来自定义机制的内核文档、实现者自己的说明，以及至少两家互不隶属的机构的实现，可以当作工程判据使用。

**有实现者一手文档支撑、但适用范围受限的**：第 4 章路径四的运行时层。虚拟 shell 与语言运行时权限模型都有实现者写明的威胁模型、默认值与绕过路径，所以「这条路径存在且能约束什么」已经不是猜测；但「它能平替操作系统沙箱」被实现者自己的文档否定，仍属未确立。第 8 章引用框架后端设计记录时也适用同一分寸：形态有据，落到具体宿主仍要靠条件句。

**属于机制描述与分类框架、而非实测结论的**：「仅 Linux 五层」「双平台三条系统级路径 + 一条运行时层路径」这套分类本身，是对公开文档的结构化归纳，不是某次实验测出来的结果。它可以指导排查，但不能读作「已在所有发行版与 macOS 版本上验证过」。

**只有一个来源类型支撑、因而需要保留余地的**：「microVM 不必然比 gVisor 安全」这一具体命题，主要出自一家厂商的分析（Vercel，2026a）。SandboxEval 提供的是检验沙箱有效性的方法论，并未比较这两种架构；把它并列为该命题的证据是不成立的（SandboxEval 作者，2025）。因此第 6 章只保留「应按威胁模型与完整部署评估」这一较弱主张。

**条件性结论**：涉及某一具体受限宿主的判断，在本次证据集里没有一手材料支撑，必须写成条件句，详见下节。

## 本轮补充材料改变了什么

补充材料带来两处必须记录的口径变化，供复核时追溯。

**运行时层从「候选」变为「有据但受限」**。初稿依据的是社区清单与检索记录，因而写成「没有任何一份一手实现文档」。补充的虚拟 bash 包 README、威胁模型与语言运行时官方安全文档推翻了这个事实断言：实现、默认值、可能被利用的途径与剩余风险都能查到。但两份实现者文档同时写明无虚拟机隔离、并建议叠加操作系统或虚拟机边界，所以结论边界没有松动——第 4、6、8 章据此改述，而不是把这条路径升格为第四条等价方案。

**框架形态从「未入库」变为「已入库、宿主前提仍缺」**。初稿把具体的远程执行后端形态视为前序会话里的内部事实，不作为证据；补充的后端设计记录把它写成可引用的公开材料，说明执行面如何隔离、凭据如何不进客户机、失败如何不回退。但目标宿主的实测环境仍未入库，因此第 8 章的条件句只调整了依据，没有取消。

同时新增的两组材料——开箱即用 microVM 框架的硬件前提矩阵、现成的 Linux 进程沙箱封装——扩展了第 3、4 章的可选实现清单，却没有新增隔离层：前者把虚拟化能力移到 macOS 侧或服务端，后者仍是命名空间与系统调用过滤的封装。

## 资料矛盾如何处置

本次调研遇到四处不一致，处理方式如下：

**Codex 的 Linux 后端**。社区清单写「Landlock + seccomp」，OpenAI 官方两份文档写「bubblewrap + seccomp-bpf」。以一手文档为准，判定为后者（OpenAI，2026a，2026b；containers/bubblewrap，2026；Anthropic，2026）。社区清单记为过时或二手描述；「早期版本是否用过 Landlock」没有证据，不作断言。

**「microVM 一定更安全」**。营销叙事与厂商分析相反；按一手分析判定为伪命题，改以完整部署与威胁模型评估（Vercel，2026a）。

**macOS 侧的 KVM 替代**。libkrun 走 HVF，Encore 的 crackling 走 VZ，两者常被合并称作「苹果虚拟化」。本文并列为两个方案，分别标注框架名，因为授权要求与能力集不同（libkrun，2026；Encore，2026）。补充材料还显示 ArcBox 的沙箱只在 Virtualization.framework 后端、M3 或更新芯片、macOS 15+ 上可用，其他组合直接返回 `FAILED_PRECONDITION`（ArcBox，2026b），进一步说明「苹果虚拟化」不是单一能力档。

**用户命名空间「可用」还是「够用」**。OpenAI 观察到部分发行版默认禁用用户命名空间、却给系统 `bwrap` 开例外；Anthropic 则指出 Ubuntu 24.04+ 允许创建但剥离能力。两者不是矛盾而是粒度差异，最终判据统一写成「带能力的非特权用户命名空间」（OpenAI，2026a；Anthropic，2026）。

## 表述上的边界

为避免读者把条件性内容当成既成事实，全文遵守三条：涉及具体宿主时一律用「若……则……」，并注明前提本身未核验；涉及框架改造时只给条件性建议，框架设计记录只支撑形态、不支撑宿主结论；不使用「已证实无解」「必然更安全」「全部支持」「已平替」这类全称判断。第 8 章会沿用这个口径。

# 第 8 章 结论与给 agent 框架的建议

## 五个可以带走的判断

**第一，缺 `/dev/kvm` 是一个局部约束，不是全局判决。** 它关闭的是 KVM 后端的轻量虚拟机；Landlock、seccomp-bpf、bubblewrap、gVisor systrap 都明确不依赖硬件虚拟化，远端托管沙箱更把隔离整个搬到服务端（Linux 内核文档，2026；gVisor 项目，2026；Vercel，2026a，2026b）。

**第二，可行性由四个正交前提决定。** 内核版本与内核安全模块配置、带能力的非特权用户命名空间、是否允许远端执行、工具链可裁剪程度——这四项必须逐项核对，任何一项通过都不能推出其他项。尤其是「用户命名空间可用」不等于「bubblewrap 可跑」（Anthropic，2026；containers/bubblewrap，2026）。

**第三，双平台有三条系统级路径，另有一条边界更窄的运行时层路径。** 操作系统原语对配统一接口、跨平台虚拟机抽象、远端执行都有完整的一手实现；虚拟 shell 与语言运行时权限模型同样已有实现者写明的威胁模型，但它们自述无虚拟机隔离、并要求叠加操作系统或虚拟机边界，因此不能当作等价方案（OpenAI，2026a；Anthropic，2026；libkrun，2026；Encore，2026；Vercel，2026b；Vercel Labs，2026a，2026b；Deno 项目，2026）。

**第四，网络出口与凭据是与进程隔离并列的边界。** 出站策略与密钥注入要在执行环境之外落实，且多家产品的公网访问默认是开启的；配置开关的名字也不等于它管住的对象。把这项当作附属配置会抵消掉进程隔离上的投入（OpenAI，2026a；Vercel，2026a，2026b；BoxLite，2026；E2B，2026）。

**第五，隔离强度取决于完整部署而非架构标签。** 「microVM 必然比 gVisor 安全」不成立；有效性需要针对真实工作负载实测（Vercel，2026a；SandboxEval 作者，2025）。开箱即用的 microVM 框架同样如此：跨平台只是把虚拟化前提移到 macOS 侧或服务端，没有把它消除（BoxLite，2026；ArcBox，2026b；E2B，2026；Kubernetes SIG Apps，2026）。

## 给 agent 框架的条件性建议

以下内容以「若……则……」表述，因为目标宿主的一手环境报告并未进入本次证据集（见第 7 章第 1 项缺口）。框架的远程执行形态已有一份后端设计记录可查，但「形态成立」不等于「该宿主可用」。

**若允许远端执行**，优先采用远程执行后端：宿主保留模型凭据与策略决策，客户侧只提供 shell 与文件系统，启动时失败即拒绝、不静默回退到宿主执行。这个形态在架构上等价于第 4 章路径三的自托管版本，也是本地零 KVM 前提下唯一能达到硬件级隔离的最小改造面；已公开的后端设计记录把它写成只实现执行与文件传输、凭据不进客户机、失败即报错的契约（Soothe，2026）。配套必须做第 5 章的六项出口检查，特别是把默认允许的公网改成默认拒绝，并核对所用开关约束的是宿主沙箱还是客户机。

**若不允许远端执行、且宿主具备带能力的非特权用户命名空间**，可以新增一个 Linux 原生轻量后端，复用第 3 章第二、三层的组合：按权限档案拼装只读/可写挂载视图，配合 `no_new_privs` 与 seccomp 过滤，并由统一接口按操作系统分派到 macOS 的 Seatbelt。这与两家 CLI 已有的做法同构，工程量主要在参数拼装与代理接线，不在新机制的研发（OpenAI，2026a；Anthropic，2026）；nsjail、Firejail、Sandbox2 与 isolate 这类现成封装可以作为实现参考，但它们要求的内核能力完全相同（Google/nsjail，2026；Firejail，2026；Google/Sandbox2，2026；ioi/isolate，2026）。

**若工作负载能限定为脚本与数据处理**，可以把运行时层作为附加约束：默认关闭网络与可选解释器、限制命令数与资源、让文件系统只存在于内存中。但实现者自己写明这不是虚拟机隔离，所以必须另有外层边界；只对可裁剪工具链的场景成立（Vercel Labs，2026a，2026b；Deno 项目，2026）。

**若不允许远端执行、且宿主四项前提全部不满足**，则没有本地内核边界可用。此时诚实的做法是在配置里显式声明「无隔离」，把防护收敛到应用层路径与命令策略，并在日志与界面上让运维看得见这个状态；不要用一个看似启动了、实际未生效的沙箱给出虚假的安全感。同时保留 `hard_deny_severities` 一类硬拒绝策略——只有在另有外层虚拟机或容器牢笼时，才应考虑放宽这类策略。

**顺序建议**：先按第 2 章四项前提做一次宿主能力盘点，再决定是否远端化；在运行时代理与凭据边界落地之前，不要先投入跨平台虚拟机抽象的自建工作。后者的工程成本（镜像工具链、能力协商、客户机内核模块匹配、特定 Apple 芯片与系统版本）在材料里被反复提及，属于确定要付的代价（Encore，2026；ArcBox，2026b）。

## 什么会改变这些结论

第 7 章列了八项缺口，其中三项会实质改变结论措辞：把目标宿主的环境探针作为独立材料入库并跑一遍对照实验，可把「若……则……」升级为实测结论；补一份运行时层在真实智能体工作负载（git、包安装、原生编译）上的可移植性对照，才能判定这条路径能覆盖多少工具链；补一次框架后端在目标宿主上的启动与失败降级实测，才能把设计契约变成可核查的行为。出现独立的第三方安全基准，才能对「microVM 与 gVisor 谁更安全」给出有依据的强弱判断。

## 收束

回到开头那个 `ls -l /dev/kvm`。它返回的只是「某一类隔离不可用」。把这个结果放进四项前提的矩阵里，选择空间其实很大：满足内核条件就走分层栈，允许远端就把隔离搬走，需要双平台就选原语对或虚拟机抽象，工具链可裁剪时再加一层运行时约束，而无论哪条路都要单独补上出口与凭据。真正需要警惕的不是缺一个设备节点，而是用一次探针的退出码，替代了对整条信任边界的设计。
